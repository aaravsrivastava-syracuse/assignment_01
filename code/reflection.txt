The main lesson from this assignment is how a module separates calculation logic from an interface. The four functions in bill.py handle the math, while the console, notebook, and Streamlit interfaces import and reuse them. This means a correction to grand_total can improve all three interfaces without repeating the formula in each one.

A potentially confusing distinction is the subtotal versus the grand total. For a $50 subtotal and a 20% tip, tip_amount returns $10, grand_total returns $60, and split_evenly returns $15 for four people. Returning only the tip from grand_total would produce $10 instead of $60. Splitting the subtotal would produce $12.50 per person and leave out the tip. Both are logical errors: the program can run but give the wrong answer.

Unit tests check individual functions, while integration tests check whether a whole interface uses those functions correctly. A failed assertion identifies the difference between the expected and actual results. To investigate the console error with a debugger, a useful breakpoint is the line that calculates per_person. Inspecting subtotal, total, and people in the VARIABLES panel would reveal which amount is being divided.

Rounding is another point that needs care. round(100 / 3, 2) produces 33.33, but three shares add up to 99.99. The function meets the assignment's requirement, although distributing the remaining cent would need an additional rule. The ValueError in split_evenly also makes the requirement explicit that people must be greater than zero.

A concrete next step is to practice stepping through the console calculation with a breakpoint and compare a failing unit test with a failing integration test. Useful boundary cases to explore are zero and negative people, a zero subtotal, and tip percentages just below and exactly at 20%. These checks help explain the behavior instead of only checking the usual $50 example.
